# Space-RPG 开发错误与AI误判总结

> **项目**: space-rpg-h5 + project-chronos  
> **开发周期**: 2026-04-10 ~ 2026-04-16  
> **整理日期**: 2026-04-25  
> **目的**: 归档开发过程中遇到的工程错误和AI产生的误判，供未来项目参考

---

## 一、工程错误（代码层面）

### 1.1 全局变量命名不一致

| 项目 | 详情 |
|------|------|
| **现象** | `APIManagerInstance is not defined` 运行时报错 |
| **根因** | `api-manager.js` 导出 `apiManagerInstance`（小写a），`game-core.js` 引用 `APIManagerInstance`（大写A） |
| **修复** | 添加兼容性导出 `const APIManagerInstance = apiManagerInstance`，双支持 |
| **教训** | JS项目应统一全局变量命名规范（camelCase或PascalCase），跨文件引用时尤其注意 |

### 1.2 占位符方法未桥接

| 项目 | 详情 |
|------|------|
| **现象** | AI响应只输出到console，不显示在UI；状态面板不更新 |
| **根因** | `GameCore.addTerminalOutput()` 和 `GameCore.updateUI()` 是占位符（只 `console.log`），未桥接到 `UIManager` |
| **修复** | 改为 `UI.addTerminalOutput()` / `UI.updateStatusDisplay()` 的代理调用 |
| **教训** | 占位符方法必须标记 `// TODO`，并在集成阶段逐一验证桥接 |

### 1.3 Game.command() 方法缺失

| 项目 | 详情 |
|------|------|
| **现象** | HTML快速命令按钮（`onclick="Game.command('/status')"`）点击无响应 |
| **根因** | `Game` 全局对象只暴露了 `processCommand()`，没有 `command()` 别名 |
| **修复** | 添加 `command(input) { this.processCommand(input) }` |
| **教训** | HTML与JS的接口约定必须在开发初期明确，避免前后端命名不匹配 |

### 1.4 Game.performRest() 方法缺失

| 项目 | 详情 |
|------|------|
| **现象** | 休息模态框无法工作 |
| **根因** | HTML调用 `Game.performRest()` 但该方法未定义 |
| **修复** | 添加方法并桥接到 `handleRestCommand()` |
| **教训** | 同上，HTML→JS调用链应作为集成检查清单项目 |

### 1.5 代码重复定义

| 项目 | 详情 |
|------|------|
| **现象** | `detectWeapon/detectRange/detectResource` 等6个方法在 `game-core.js` 中被定义了两次 |
| **根因** | 不同开发轮次添加时未检查已有实现 |
| **修复** | 删除重复定义，保留逻辑更完善的版本 |
| **教训** | 大文件修改前应先搜索现有实现，避免重复代码 |

## 二、AI误判与设计缺陷

### 2.1 AI工具调用JSON解析失败

| 项目 | 详情 |
|------|------|
| **现象** | `analyzeActionForTools()` 返回的JSON解析频繁失败 |
| **根因** | AI响应格式不稳定，常在JSON外包裹自然语言说明，或字段名/结构不符合预期 |
| **修复** | 三层防御：①强制JSON格式prompt → ②安全 `parseToolAnalysis()` 验证字段 → ③降级为关键字提取 |
| **教训** | **永远不要信任AI返回标准JSON**。必须：严格prompt约束 + 后解析校验 + 降级兜底 |

### 2.2 AI输出格式不一致（跨提供商）

| 项目 | 详情 |
|------|------|
| **现象** | Claude响应用 `content[0].text`，OpenAI/DeepSeek用 `choices[0].message.content`，切换提供商就崩溃 |
| **根因** | 响应处理只覆盖了一种格式 |
| **修复** | `processResponse()` 按 `currentProvider` 分支处理，加通用降级 |
| **教训** | 多提供商API对接时，响应解析必须按提供商分支+通用兜底，不能只测一个就上线 |

### 2.3 AI"自造数值"（数值幻觉）

| 项目 | 详情 |
|------|------|
| **现象** | AI在叙事中编造不存在的战斗伤害/恢复量/距离数值，与工具计算结果矛盾 |
| **根因** | AI无法区分"叙事性描述"与"游戏机制数值"，倾向于生成看似合理但实际编造的数字 |
| **修复** | Validator后处理校验：检测AI输出中的数值与工具计算是否匹配，不匹配则警告覆盖 |
| **教训** | **AI+游戏机制的核心矛盾**：AI想讲故事，机制需要精确数值。解决方案是"AI只叙事，工具只算数"，AI绝不碰数值 |

### 2.4 AI注册NPC边界模糊

| 项目 | 详情 |
|------|------|
| **现象** | 代词（"他""她"）、通用称谓（"商人""老人"）、群体（"村民们"）被误注册为NPC |
| **根因** | 初始提取逻辑太宽泛，只要首字母大写或引号内文字就可能注册 |
| **修复** | 8种提取模式优先级排序 + `FILTER_WORDS` 通用过滤词表 + 名字长度2-12字符限制 + `name@location` 去重 |
| **教训** | AI输出提取的边界条件必须明确：什么注册、什么不注册、同名怎么处理，都要写死规则 |

### 2.5 searchActs返回mock数据

| 项目 | 详情 |
|------|------|
| **现象** | 幕文件搜索总是返回硬编码的"星际探索者号/张三/织星"等模拟结果 |
| **根因** | 开发时写的mock数据忘了替换，`ActManagerInstance` 的真实搜索未被调用 |
| **修复** | 移除全部mockResults，改为调用 `ActManagerInstance.searchByKeyword()` |
| **教训** | Mock数据必须标记 `// MOCK: 需替换`，集成阶段必须逐一清除 |

## 三、系统性问题

### 3.1 API Key安全与持久化矛盾

| 矛盾 | 说明 |
|------|------|
| **安全需求** | API Key不应存入localStorage（XSS可窃取） |
| **体验需求** | 页面刷新后Key丢失，每次都要重新输入 |
| **方案** | sessionStorage（标签页内持久，关闭自动清除）+ `hasApiKey` 标记判断是否已配置 |
| **教训** | 安全与体验的权衡是API类项目的永恒课题，sessionStorage是合理的折中 |

### 3.2 fetch无超时控制

| 项目 | 详情 |
|------|------|
| **现象** | API无响应时页面卡死，用户无法操作 |
| **根因** | 原生 `fetch()` 没有超时参数 |
| **修复** | `AbortController` + 30秒超时 + 重试退避策略 |
| **教训** | 所有网络请求必须有超时+重试+用户可中断，这是基本工程素养 |

### 3.3 状态描述阈值不一致

| 项目 | 详情 |
|------|------|
| **现象** | 同一个健康值，`ui-manager.js` 显示"受伤"（阈值60），`game-state.js` 显示"正常"（阈值70） |
| **根因** | 两个文件各自硬编码了状态描述阈值，数值不同 |
| **修复** | 应统一提取为 `UI_CONFIG.thresholds`，单一数据源 |
| **教训** | 同一语义的配置散落在不同文件中，必然导致不一致。必须集中定义 |

### 3.4 硬编码泛滥

| 规模 | 说明 |
|------|------|
| **20项 / ~80个数值** | 战斗系统12个、技能检定6个、恢复量8个、导航2个、UI/存储/声望等50+个 |
| **根因** | 快速原型阶段图方便直接写数字，未提取为配置常量 |
| **教训** | 从第一天就用配置对象（`COMBAT_CONFIG`等），不要指望"后面再清理"。后面通常不会清理 |

## 四、AI作为开发助手的误判

### 4.1 AI审查报告的乐观估计

| 误判 | 实际 |
|------|------|
| "修复后AI功能稳定性提升80%" | 无实测数据支撑 |
| "API成功率从70%提升到95%" | 基准数据本身就是估计值 |
| "预计改动量约100行引用替换，风险低" | 硬编码清理实际涉及13个文件的跨模块引用，风险不低 |

**教训**: AI生成的"预期改进"数据多为信口开河，不要用这些数字做决策

### 4.2 AI修复方案过度设计

| 案例 | 说明 |
|------|------|
| APIKeyManager类 | 建议新建独立类管理密钥，实际只需要sessionStorage读写3个方法 |
| RequestQueue类 | 建议实现完整请求队列+速率限制，实际RPG游戏不存在并发请求场景 |
| APIConnectionManager类 | 建议连接状态监控，实际玩家手动测试连接就够了 |

**教训**: AI倾向给出"教科书式"的完整方案，但MVP思维要求只做最小必要实现。对AI方案必须裁剪

### 4.3 AI代码审查遗漏交互链路

| 遗漏 | 说明 |
|------|------|
| 代码审查评分4/5 | 实际交互链路3处断裂（command/performRest/addTerminalOutput），用户基本功能不可用 |
| 审查聚焦代码质量 | 忽略了HTML→JS接口一致性检查 |

**教训**: AI代码审查容易陷入"代码美学"而忽略"功能可用性"。必须补充端到端链路检查

## 五、关键教训提炼

| # | 教训 | 适用范围 |
|---|------|----------|
| 1 | **永远不信任AI返回JSON** — 严格prompt + 后校验 + 降级兜底 | 所有AI API对接 |
| 2 | **AI只叙事，工具只算数** — AI绝不碰游戏机制数值 | AI+游戏系统 |
| 3 | **占位符必须标记TODO** — 集成阶段逐一验证桥接 | 快速原型开发 |
| 4 | **第一天就用配置对象** — 不要指望后面再清理硬编码 | 所有游戏开发 |
| 5 | **跨文件命名必须统一** — camelCase或PascalCase选一个贯彻 | JS项目 |
| 6 | **AI方案必须裁剪** — 教科书方案≠MVP方案 | AI辅助开发 |
| 7 | **端到端链路检查不可省** — 代码美学≠功能可用 | 所有项目 |
| 8 | **AI审查数字不可信** — "提升80%"之类都是编的 | AI辅助评估 |
| 9 | **同一配置集中定义** — 散落必然不一致 | 配置管理 |
| 10 | **Mock数据必须标记** — 集成时逐一清除 | 开发流程 |
